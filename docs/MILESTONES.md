## Where the product is

**Built and operational:** Owner authentication, Task core, the Recipient capability web loop, Gmail ingestion and polling, the AI suggestion path, Gmail forwarding and assignment email, the Owner web experience foundation, and the Android Owner client through organize, assign, and follow-through. Owner Capture on Android now uses the S3 interpretation path (read-only proposals), not direct Task create.

**S3 complete at the locked capture-to-proposal boundary (not Production-activated):** Owner Android Capture → durable exact-retry identity → Owner-authenticated `POST /api/v1/manual-captures` → shared backend interpretation → 0..N canonical TaskSuggestions → Android read-only proposal result. **S3.1** (shared interpretation application service + canonical `InterpretationRun` / TaskSuggestion persistence), **S3.2** (Owner manual-capture HTTP/API), and **S3.3** (Android capture switch, encrypted 24-hour pending-capture retry store, read-only 0/1/N proposal results) are **implemented**. Capture creates no canonical Task. Provider composition remains default closed, so the route answers `503` until `INTERPRETATION_AI_ENABLED` is set; no worker or cron reaches the service; no Production activation has been authorized. Legacy `POST /api/v1/tasks` still exists, and the unused Android direct-create implementation remains in source for rollback — neither is removed.

**S4 complete at the locked presentation boundary:** **S4.1** Owner web, **S4.2** Recipient web, and **S4.3** Android are **implemented**. Shipped Owner web, Recipient `/c/{token}`, and Android Owner surfaces use the canonical dark presentation in [BRAND.md](../BRAND.md) (D172–D175). **`/` and `/login` remain outside S4 by design** and keep the unmigrated light identity/onboarding presentation. Shared/legacy token consolidation remains later and separately unauthorized. S4 authorized no proposal-lifecycle implementation, no responsibility-selection implementation, and no other deferred product capability.

**S5 complete at the locked Android Owner proposal-lifecycle boundary (D176):** Capture → shared interpretation → 0..N TaskSuggestions → Owner review → Accept / Edit / Dismiss. **S5.1** (Android proposal lifecycle client plumbing), **S5.2** (Accept + affirmative Me / saved-Recipient responsibility selection + canonical Task transition + `approvedTaskId` lost-response recovery), and **S5.3** (narrow proposal wording edit, lossless mixed-kind Edit round-trip, and Dismiss) are **implemented**. Accept requires an affirmative Me / Owner or saved-Recipient choice; Owner/Me is never inferred. Recipient selection records D168 responsibility only and does not create assignment, handoff, or delivery. Successful Accept creates the canonical Task and opens existing Task detail. Edit changes authorized wording only while preserving structural and kind-specific canonical fields. Dismiss resolves the intended proposal only and creates no Task. Merge remains excluded. No deadline, priority, or reminder controls. No Production AI, flag, or cron activation, and no Owner Acceptance Week execution.

**S6 complete at the locked Owner Follow-Through Foundation boundary (D177, D178):** Android Task-detail view/set/change/remove of the existing date-only organization-local due date, independent Automatic Reminder ON/OFF for the existing D105 advance occurrence, truthful read-time due/overdue derived from that canonical date, and the additive Task-read `dueLocalDate`. **S6.1** (canonical due-date reads), the D178 persisted advance preference, and **S6.2** (Android Task-detail Scheduling) are **implemented**. S6 uses the existing single D105/D106 reminder model with the D105 advance independently Owner-optional; multiple Owner-controlled reminders remain deliberately deferred, not rejected. No reminder delivery, no A8 flag or cron enablement, no second follow-through engine, no Task-list indicator, and no OAW or P2.2.

**S7 complete at the locked Gmail Review with Rocket boundary (D179, D180):** Owner-authenticated Gmail intake over existing eligible A5 Gmail data; Owner-initiated Review with Rocket through the Gmail-specific adapter into the existing shared interpretation service; `gmail` source kind and truthful Gmail provenance; D161 Owner-initiated idempotency and committed-occurrence replay; 0..N canonical TaskSuggestions left for the existing S5 proposal lifecycle; Android Gmail intake/Review UI; Gmail-specific Exclude Sender with intake filtering, server-side new-Review refusal, and Android Exclude Sender + Undo. S7 is Owner-initiated interpretation, not continuous automatic interpretation. A6 remains existing compatibility/operational infrastructure and is not the S7 path. No Production `INTERPRETATION_AI_ENABLED` activation, no OAW, and no P2.2.

**Built and deliberately inert:** the reminder and Owner-notification engines. The scheduling domain, persistence, Owner reminder APIs, occurrence processing, real Gmail transport, and the Owner attention surfaces are all deployed, but every feature flag is absent and no scheduler invokes either worker, so nothing sends. Enabling any of it requires its own authorization.

**Not built:** Messages capture, call prompts, the voice pipeline, retention workers, learning signals, and private-deployment hardening. Merge, proposal inbox/list-browsing beyond the capture decision loop, Recipient creation inside Accept, automatic assignment/handoff/delivery, and the remaining D176 exclusions remain separately unauthorized. **SMS/text Review with Rocket is authorized by D181 and is not implemented.** Reminders enablement, the attention system, sender-management UI, and allow lists remain later work. **S7 — Gmail Review with Rocket is complete** at the locked Gmail boundary (D179, D180) and is not Production-activated.

**Next:** **SMS/text Review with Rocket** (D160 product direction; implementation authorized by **D181**, not begun), then final pre-OAW integration/readiness, a consolidated Android candidate build, then explicit OAW authorization / lifting of D159. See [Forward sequence](#forward-sequence).

## Owner Acceptance Week

**Status:** formal product gate (D142). **Deferred — must not be executed until the Owner re-authorizes it** (D159). No separate OAW procedure document is active; surviving law is **D142**, **D159**, and this section.

**Exit criteria (all required):**

1. Rocket is the Owner's primary task system during the window
2. Real work captured daily on the native client
3. Real Recipient handoff completed
4. External notes no longer required for ordinary follow-through
5. Usability issues documented
6. Owner explicitly approves or withholds resuming operational enablement; **silence is not approval**

P2.2 entry requires an OAW pass (or recorded conditional Go) plus explicit Owner Go.
