**A8.3b Owner reminder APIs and contracts: complete, audited, and remediated.** Three Owner-authenticated operations exist on `/api/v1/tasks/{taskId}/reminder`: `GET` reads reminder state, `PUT` establishes or materially changes the canonical due date, and `DELETE` removes it and stops the schedule. **A8.3b failed its first critical audit; the findings below are remediated.** The audit is the reason four behaviours differ from the original slice:

- **Task-state eligibility (F1).** There was no gate: a `PUT` established an _active_ schedule on a completed, dismissed, or Waiting Task, so a future worker would have found claimable occurrences for finished or explicitly paused work. D107 already answered this, so the rule is applied rather than invented — a `completed` or `dismissed` Task is refused with 409, and a `waiting` Task's schedule is created or re-generated directly in `suspended_waiting` with no claimable occurrence. The policy lives in `packages/domain/src/reminders/eligibility.ts` so the A8.4a worker and lifecycle wiring read one source. `GET` and `DELETE` remain allowed for every status: reading history is not scheduling, and removal can only ever reduce reminder activity.
- **Concurrency (F2, F5).** Mutations required a _Task_ `If-Match`, but a reminder write deliberately does not bump `Task.version`, so two Owners could each hold a valid "current" token. On real PostgreSQL the audit produced both a lost update — a committed `reminder.due_date.removed` event behind a surviving active schedule — and a deadlock that escaped as a 500, because establishment and generation-change wrote the schedule before the Task while removal wrote the Task first. The reminder resource now carries its own version (`task_reminder_schedules.reminder_version`) surfaced as a `task-reminder` ETag that `PUT` and `DELETE` require; all three mutation transactions lock the Task row first, so there is one lock order; removal stops only the generation its caller observed; and a serialization refusal maps to the typed concurrency error, never a 500. Proven with two connections against PostgreSQL 16 in `apps/web/__tests__/owner-reminder-concurrency.pg.test.ts`, which PGlite cannot substitute for.
- **Audit truthfulness (F4).** `reminder.schedule.changed` recorded only that something changed. Events now carry the prior and new local dates, the prior and new generations, and the resulting state, and a reactivation is recorded under its own action rather than as an ordinary change.
- **Response hygiene (F3, F6, F9).** The body validator was a denylist that silently accepted `reminderTime`, `presetInterval`, and any unknown field while OpenAPI declared `additionalProperties: false`; it is now an exact allowlist. `Cache-Control: no-store` is applied by one route finalizer to every response including service-thrown errors, rather than at each success branch. #### Deferred lifecycle gate — CLOSED by the A8 lifecycle wiring slice

**No worker may scan, claim, or send until Task lifecycle transitions are wired transactionally.** This was the gate, stated once and durably so it could not be satisfied by inference. It is now **closed**; the requirements and the reason for the deferral are kept below as the record of what had to be true, and the section that follows records how each was met.

D107's stopping and suspending rules are a set: Waiting suspends, completion and dismissal stop, due-date removal stops. A8.3b implemented due-date removal, and its eligibility gate additionally prevented a terminal or Waiting Task from _acquiring_ a live schedule. Neither was the same as reacting to a transition: a schedule established while a Task was open stayed `active` after that Task completed, and entering Waiting did not suspend an existing schedule.

Before the first A8.4a scan or claim path exists, the wiring must guarantee:

- entering Waiting suspends;
- leaving Waiting resumes from the next **future** eligible occurrence;
- completion stops;
- dismissal stops;
- no backlog is replayed on resume;
- generation does **not** change solely because of Waiting;
- Owner and Recipient actor attribution follows D107;
- reopen and restore semantics are **decided** before they are implemented.

Why it was not done in A8.3b: entering and leaving Waiting is reachable by **two** actor kinds — the Owner through `POST /tasks/{taskId}/waiting` and `/resume`, and a Recipient through the `mark_task_waiting` capability scope — and both run through the shared `persistCapabilityAction` transaction, so suspending reminders there means changing a Recipient-facing A4/A7 code path rather than the Owner reminder surface. Implementing one member of the set alone would also be actively wrong. Nothing sends in A8.3b, so the gap had no delivery consequence yet, and `apps/web/__tests__/owner-reminder-routes.test.ts` pinned the behaviour under "task lifecycle boundary" so it could not be forgotten. No second, parallel "pause reminders" control was invented.

#### A8 lifecycle wiring: complete, closing the deferred lifecycle gate

**Reminder state now follows Task status, in the Task's own transaction.** Every authoritative status transition — Owner `/waiting`, `/resume`, completion, and dismissal, and the Recipient `mark_task_waiting` and completion capability actions — converges on `persistCapabilityAction`, which reconciles the reminder schedule before the status commits. Reconciliation is a persistence concern in `packages/db/src/transactions/a8-lifecycle-reminder-effects.ts`, not a route-level side effect, because the authoritative transition happens below the route; adding it above would have been a second transaction and would have left a window where a committed terminal Task still held a claimable occurrence. Each requirement of the gate above:

- **Entering Waiting suspends.** An `active` schedule becomes `suspended_waiting` with its claimable occurrence cleared. A `stopped` schedule is left alone — never re-labelled as merely paused — and a Task with no schedule gets none.
- **Leaving Waiting resumes from the next future occurrence.** Only a schedule suspended _because of_ Waiting resumes. The next occurrence is computed **strictly after** the resume instant, so nothing that would have fallen during Waiting is replayed and nothing sends merely because time passed. The due date is untouched.
- **Completion and dismissal stop**, with reasons that distinguish them from each other and from due-date removal, clearing all claimable next-occurrence fields, preserving generation and every delivery attempt, and deleting no row.
- **No backlog, and no generation change.** Generation and the delivered-overdue count survive a Waiting round trip intact, so a pause neither resets the D106 ceiling nor earns extra reminders. If the preserved count has already reached the ceiling, resume records the schedule as requiring Owner attention rather than manufacturing a fresh occurrence. The no-backlog rule covers the **advance** occurrence too: one that Waiting spanned is permanently skipped rather than replayed — see the remediation below.
- **Attribution follows D107.** The derived reminder event carries the actor who caused the transition — Owner for an Owner action, capability for a Recipient's — with a distinct action name marking it as derived rather than directly requested. A Recipient's action is never attributed to the Owner, and no autonomous worker actor was introduced. Notes carry state, generation, and reason only: no message content, provider identifier, or capability token.
- **Reopen and restore are decided.** No path today moves a terminal Task to a nonterminal status, and terminal → Waiting is unreachable. The decision, recorded before any such path can exist: reopening does **not** reactivate a terminally stopped schedule; an explicit Owner re-save is required, consistent with D109. Recorded in [STATE_MACHINE.md](STATE_MACHINE.md) and pinned by test.

**Three re-audit findings closed in the same slice**, because each becomes reachable the moment a worker or a lifecycle caller contends:

- **H1 (high).** The removal transaction applied its compare-and-set only on the branch where the caller had _observed_ a live schedule; the other branches had no transactional precondition, so a removal could clear `tasks.due_local_date` and commit `reminder.due_date.removed` while a concurrent transaction activated the schedule — reproduced on real PostgreSQL. Removal now re-reads the schedule under the Task lock and requires a precondition on **every** branch, including absence and the already-stopped case, where the reminder version is bumped so that clearing the due date is itself a serialization point. Repeated PostgreSQL rounds in this slice found one more instance of the same root cause, fixed here: the "nothing to remove" short-circuit sat _above_ the transaction and decided from two non-atomic reads, so under contention it could pair a due date already cleared by a winning removal with a schedule version from before it and answer 200 with a superseded ETag — a stale caller told it had succeeded. That decision moved under the lock, behind the precondition. Establishment and generation change additionally re-check Task status under the lock, so a dismissal cannot race a reactivation into an active schedule on a dismissed Task. The loser writes nothing and answers 409 or 412; nothing escapes as a 500. Fixed in the persistence transaction contract, not the web caller.
- **M1 (medium).** The A8.3a establishment primitives — the ones A8.4 will call — wrote the schedule before the Task and took no Task lock. All reminder mutations now share one order: lock the Task row, read the schedule under that lock, mutate the schedule, mutate the Task, write the audit event, commit. No table locks; contention stays scoped to one Task.
- **M2 (medium).** The concurrency helper inspected only the last reminder audit event, so a truthful final state could hide an untruthful history. It now asserts over the full sequence: the event count reconciles with the persisted reminder version, no losing transaction leaves an event, and the final schedule is compatible with everything the trail claims. Schedule invariants are checked directly against the database — no active schedule behind a null due date, and no claimable occurrence on a stopped or suspended schedule.
- **L1 (low), decided.** `reminder_version` stays the **Owner-controlled configuration** version rather than a whole-representation validator: worker-owned `nextOverdueOccurrence` and `overdueDeliveredCount` do not move it, so a delivery cannot invalidate an Owner's in-flight edit through no fault of the Owner. The API contract says so explicitly instead of implying otherwise. Responses remain `no-store`, so nothing depended on the token as a cache validator.

**Evidence.** `packages/db/__tests__/a8-lifecycle-reminder-effects.test.ts` (reconciliation, idempotency, no-backlog resume, ceiling guard, D107 attribution), `packages/db/__tests__/a8-3b-reminder-concurrency-token.test.ts` (H1 precondition on every branch, eligibility re-checked under the lock), `apps/web/__tests__/recipient-capability-routes.test.ts` (capability-triggered suspend, resume, and stop, end to end), `apps/web/__tests__/owner-reminder-routes.test.ts` (the former "task lifecycle boundary" tests, inverted into proofs of the wiring), and `apps/web/__tests__/owner-reminder-concurrency.pg.test.ts` on real PostgreSQL 16 with two connections (H1 regression in both arrival orders, lifecycle versus Owner races, and a lock-order proof exercising the former A8.3a establishment path against an Owner mutation).

The remediation below added one additive migration. **Still absent:** no worker, scan, claim, delivery, Gmail path, cron, scheduled function, feature flag, or UI. #### A8 lifecycle audit remediation: two High findings closed

The lifecycle-wiring audit passed the wiring itself and found two High-severity defects, both about a state that could be _described_ untruthfully rather than corrupted. Both are fixed here.

- **H-1 (high): the immaterial-repeat `PUT` decided a no-op from two unlocked reads.** Re-saving the date a live schedule already carries must write nothing — resetting the generation would reset the delivered count, and repeated saves would then defeat the D106 ceiling. But the route service decided it, comparing the requested date against a schedule it had read and then reading the canonical due date in a second statement. Those are different snapshots. Racing a `DELETE` on real PostgreSQL, the audit got back `200` describing an **active** schedule with a `NULL` due date and a live future occurrence, carrying an ETag for a version already superseded — a state that had never existed at any instant. Nothing was persisted wrongly, because a no-op writes nothing; the API simply asserted a fiction. The decision moved into `persistOwnerReminderGenerationChange`, which takes the Task row lock, verifies the caller's reminder version **first**, then reads the schedule and the canonical due date under that one lock and requires all three of a non-stopped schedule, an immaterial date, and a canonical due date that agrees with the schedule's own. That third condition is what makes the response coherent by construction: the caller projects it from the schedule alone and cannot pair it with a due date from elsewhere. A stale caller now loses with 412 instead of being told its no-op succeeded.
- **H-2 (high): a Waiting period could span the advance reminder and leave it looking pending.** Suspension deliberately preserves `advance_disposition = 'scheduled'`, which is right — a Task that waits an hour and resumes before its advance morning must still get that reminder. But resume armed only the next _overdue_ occurrence and never revisited the advance one, so a Task that waited past its advance morning came back **active** still carrying a scheduled advance occurrence whose instant had passed. No worker existed to act on it, but the row asserted a reminder was pending that must never be sent, and the first due-scan would have had to invent the product rule. The rule is now decided and binding: **an advance occurrence a Waiting period spanned is permanently skipped for that generation and never replayed as backlog.** Resume marks it `skipped_waiting_elapsed` — a new, additive disposition value, deliberately distinct from the establishment-time `skipped_window_elapsed`, because "the Owner chose the date too late" and "the Recipient's Waiting period covered the reminder" are different facts and the history must be able to say which. The occurrence's own local date and instant survive untouched as history. The boundary is `<=`, stated once in the A8.2 domain (`hasAdvanceOccurrenceElapsed`), so resuming at exactly 09:00 on the advance morning is too late in the same way a generation established at that instant gets no advance reminder. Three states are left alone: a disposition that is not `scheduled`, an occurrence still strictly in the future, and an occurrence with a delivery-attempt row already against it — relabelling that last one would make the schedule and the attempt history disagree.

**Schema.** One additive migration, `20260731230000_a8_advance_waiting_skip`: `ALTER TYPE "ReminderAdvanceDisposition" ADD VALUE 'skipped_waiting_elapsed'`. It rewrites no row, invalidates no existing value, and was tested applied from empty and over the existing seven migrations. The contract enum gained the same value, since the `GET` response reports the disposition and would otherwise return a value the contract does not admit. **Not applied to Production.**

**Test hardening.** The concurrency helper used to exempt any success whose ETag equalled the token it was given, treating it as a harmless no-op and comparing it to nothing — which is precisely why H-1 survived a suite built to catch it. Every success is now checked for internal coherence, and a non-mutating success must reproduce the whole prior representation field for field. A per-round cleanup that swallowed its own rejection (`prisma.task.deleteMany(...).catch(() => undefined)`, which could never have succeeded, since dependent rows reference the Task) was replaced by an ordered reset that is allowed to throw.

**Evidence.** `apps/web/__tests__/owner-reminder-concurrency.pg.test.ts` (immaterial `PUT` versus `DELETE` and versus a completion stop, both arrival orders, repeated rounds), `apps/web/__tests__/reminder-advance-waiting-skip.pg.test.ts` (Owner- and capability-triggered Waiting round trips on real PostgreSQL, plus the direct SQL invariant query), `packages/db/__tests__/a8-lifecycle-reminder-effects.test.ts` (advance boundary at, before, and after the instant; already-skipped and already-attempted history preserved; spring and fall DST; idempotency; generation and count preserved), and `packages/domain/__tests__/reminder-schedule.test.ts` (the `<=` boundary and its agreement with the establishment decision).

The A8 lifecycle re-audit measured that directly and it is **not true**: with the pre-fix unlocked no-op branch restored, 240 rounds of that suite failed to fail. #### A8.4a worker-safety foundation and occurrence lifecycle: APPROVED

> **Status: implemented, audited, remediated, re-audited, and APPROVED.** The critical worker-safety audit of `cfb733b4` failed with two Blockers and three High findings. All five are fixed and the section below is rewritten to describe what the code now does rather than what the original slice claimed. The focused remediation re-audit of `68474a26` then re-verified each of the five by tracing the call path, running 20 consecutive PostgreSQL 16 rounds, and reintroducing each original defect out of committed history to confirm the new guards reject it — and found the implementation correct. It failed only on documentation wording and two missing regression tests, which the documentation-and-test remediation closed. **A8.4a is approved, which unblocked A8.4b.** Approval is a statement about the code and its evidence, not about deployment. **A8.4a code was subsequently deployed to Production as part of `ee5e82a`, at a time when no A8 migration had been applied there and no reminder cron job existed** — the mismatch recorded as the incident at the top of this document, now closed by the 1c schema repair. Approval never authorized that deployment; a push to `main` produced it automatically. The findings and their fixes: [A8.4a audit remediation](#a84a-audit-remediation-recovery-and-settlement-safety).

**A8.4a builds the machinery a reminder worker needs to be safe, and deliberately does not build the send.** At A8.4a the only transport that existed was a fake one, delivery was off unless an environment variable was set to exactly `"true"` and it was set nowhere, no cron job invoked anything, and nothing imported Gmail. What A8.4a contributed is the occurrence lifecycle: claim, recover, guard, finalize. **A8.4b.1 adds the real overdue Gmail transport on top of it without changing any of it** — delivery is still off everywhere, no cron job exists, and `lib/reminders` still imports no provider.

**The occurrence row is the duplicate-prevention authority.** Occurrence identity is `(schedule, generation, occurrence kind, local calendar day)`, unique in the database since A8.3a. Everything else — the schedule lease, the scan order, the batch bound — is an efficiency concern that may be lost without consequence. Only the occurrence row decides whether a Recipient hears about the same morning twice.

**F1: a delivery a provider accepted is never rolled back.** The audit's finding was that `persistSuccessfulOverdueDelivery` recorded the success, incremented the count, and armed the next occurrence in one transaction with the latter two compare-and-set on the generation — so an Owner changing the due date mid-call aborted the transaction and took the row saying "this Recipient was emailed" down with it. The email had still been sent, and the next scan would send it again. Finalization runs in two phases: the occurrence is terminalized **unconditionally**, fenced only on claim ownership; then the schedule effect is applied through `updateMany` statements whose zero-row result is an expected no-op rather than an error. A superseded generation, a suspension, a stop, or a completion simply does not receive the count.

**Correction, made in the A8.4a remediation.** This paragraph previously said the two phases shared **one** transaction, on the grounds that "the second cannot abort the first", and went on to argue that sharing was strictly better than splitting. That was wrong, and the critical audit proved it by fault injection: zero-row tolerance covers the _expected_ failures and nothing else, so a CHECK violation or any unexpected error raised inside phase two aborted the whole transaction and took the record of a sent message with it. The two phases are now two transactions. The divergence the single transaction was chosen to avoid — occurrence terminal, schedule un-advanced — is real, and is handled by being _representable_: `schedule_settled_at` is null on such a row, the settlement sweep finds it, and settlement is idempotent, so collecting the debt late produces the same schedule as collecting it on time. A rolled-back delivery record left nothing behind to find.

**Counting obeys D106 exactly.** A success increments the per-generation count once, only for an `overdue` occurrence, only while the generation still matches and the schedule is still active. An advance send never counts. Neither does ambiguity, retryable failure, permanent failure, a skip, a claim, or a success whose generation was superseded mid-flight — that last one keeps its truthful record and is counted against nothing.

**F2: a claim is a bounded lease with a fencing token.** `reminder_delivery_attempts` gains claim expiry, a monotonic `claim_sequence`, and `provider_call_started_at`. A worker may take an unclaimed occurrence, reclaim an expired pre-provider one, or be refused with a reason it can act on: `lease_held`, `in_flight_unknown`, `already_terminal`, or `retry_budget_exhausted`. Every takeover is one conditional update fenced on the sequence the caller observed, so two workers reclaiming the same abandoned lease produce one winner and one refusal rather than two claimants who both believe they own it. A stale claimant cannot finalize, release, or mark in-flight over a successor.

**The recovery rule turns on one committed fact.** `provider_call_started_at` is written **before** the transport is invoked, never after. An expired lease without it means nothing left the building, so the occurrence returns to the pool. An expired lease with it means a provider may hold the message and nobody can prove otherwise — so the occurrence is finalized `ambiguous`, consumes its local day, and is never retried. Marking afterwards would make a crash mid-call indistinguishable from a crash before it, and the recovery rule would resend. Ambiguity is recorded as ambiguity rather than as success: nothing writes `provider_accepted_at` for an outcome whose whole content is that acceptance is unknown. The marker describes the **current** attempt: a retry takeover clears it along with the acceptance fields, so a crash before the new attempt's own call is recovered as "never sent" rather than misread as ambiguous.

**Recovering an occurrence is not ending the series.** The recovery that finalizes an abandoned in-flight occurrence also computes the next occurrence with the same A8.2 domain call the live path uses, and settlement arms it while the schedule is still active at the matching generation. If the schedule moved on, the terminal occurrence stands and the newer schedule is untouched. An active, eligible schedule never finishes recovery with nothing armed.

**What recovery does not do, recorded so nobody assumes otherwise.** The sweeps discharge four classes: settlement debt, expired pre-provider claims, abandoned in-flight claims, and exhausted retry budgets. They do **not** repair a schedule that is already `active` with nothing armed — the shape the B1 defect produced. That state has no occurrence row to sweep and no marker to key off, so the processor scans past it silently: it is neither fixed nor flagged. The remediation re-audit confirmed this by seeding one and running the processor five times. It carries no production exposure, because reaching that state required running the pre-fix code and **no A8 migration is applied in Production**, so no such row can exist there. If an A8 migration is ever applied to a database that has run pre-fix worker code, that database needs a one-off reconciliation query — `status = 'active' AND next_overdue_occurrence_at IS NULL` — before the worker is trusted. Detecting it at runtime would mean arming an occurrence from a schedule whose history the worker cannot see, which is a scheduling decision persistence is not allowed to make (D103).

**A retry reuses the occurrence row.** D109's identity is the occurrence, not the attempt, so forging a second row for a retry would be forging a second occurrence and the one-success-per-local-day index would be guarding the wrong thing. Three attempts are permitted; the third spends itself as a `permanent_failure` with `retry_budget_exhausted` rather than recording a retryable failure nobody may claim, which would leave the schedule scanning an occurrence it could never finish. An exhausted budget is also terminalized when it is reached by a _crash_ rather than by a rejection: a worker that died on its last permitted attempt before marking a provider call leaves an occurrence no worker can claim and none has finished, and a sweep closes it the same way. Before the remediation that state was a permanent hot loop — scanned, refused, released, forever.

**A-A: a lease is not a processed occurrence.** `hasProcessedAdvanceOccurrence` counted any attempt row, including a bare `claimed` lease, so a worker that claimed an advance occurrence and died would have frozen that advance forever — unreclaimable, because the unique identity refuses a second claim. It is replaced by `hasTerminalAdvanceOccurrence`, and the schedule's advance disposition is settled from the occurrence outcome: success → `delivered`, truthful skip → `skipped_not_eligible`, permanent failure → `failed_permanent`, ambiguity → `ambiguous`, retryable → unsettled and still deliverable. An advance already truthfully skipped at establishment or by a Waiting period is never relabelled.

**Correction, made in the A8.4a documentation remediation.** This paragraph previously said the disposition was settled in the **same transaction** as the occurrence outcome, and that the two "cannot disagree, because one transaction writes both". That stopped being true when H1 split finalization into two transactions. The disposition is now settled in **phase B**, so it can lag the occurrence outcome for as long as the settlement debt is outstanding. They cannot disagree _durably_, which is the property that matters: an unsettled terminal occurrence is discoverable debt, settlement is idempotent, and the worker discharges it before doing anything else.

**F6: the schedule lease is a scan hint, explicitly.** It bounds wasted queries and nothing else. It is now fenced on exact claim identity so a stale holder cannot release a successor's, but delivery finalization does not consult it at all. There are not two correctness systems that can disagree; there is one, and it is the occurrence row.

**F7 and F8: one public success path.** `finalizeReminderOccurrence` loads the occurrence and verifies its kind, schedule, generation, and pre-terminal state rather than trusting the caller — an advance occurrence physically cannot reach the counting branch. `recordReminderDeliveryOutcome` is renamed `recordTerminalOccurrenceOutcomeUnsafe`, kept module-private, and **removed from both `@aicaa/db` and `@aicaa/db/runtime`**; a source guard fails the build if it reappears in either barrel.

**H-B: the regression guard is structural, not timing-dependent.** See the correction recorded under the lifecycle remediation above. `apps/web/__tests__/a8-4a-worker-safety-guards.test.ts` reads the source and fails if the Owner reminder service decides materiality, if a no-op is constructed outside the locked transaction, if the raw success writer is exported, or if any processing source imports Gmail. It rejects the pre-fix design deterministically. The PostgreSQL race suites validate behaviour under contention and are explicitly **not** the sole regression mechanism.

**H-A: the Owner `GET` projects one snapshot.** It read the schedule and the canonical Task due date as two independent unlocked statements, and racing a `DELETE` returned an active schedule behind a null due date — each half true, of different moments. `readCoherentReminderProjection` now reads both inside one `RepeatableRead` transaction. No write lock is taken for an ordinary read, and `Cache-Control: no-store` is unchanged.

**F10: constraints for the states worker code must never produce.** A claim's owner and acquisition time move together; a lease requires an owner; a settled occurrence holds no live expiry; a provider call requires a claim; acceptance requires an in-flight marker and a `success` outcome; a message reference requires acceptance; and a non-active schedule holds no scan lease. The migration also **backfills** `claim_sequence = 1` for claims written under A8.3b's indefinite marker, without which the fencing constraint would reject data that already exists — a defect the from-existing-state migration test caught and that applying from empty could not have.

**F11: the worker scan is global, bounded, and deterministically ordered.** One Owner organization exists, and a cron-driven worker that enumerated organizations in application memory would make a fairness decision in the least observable place available. `listDueReminderSchedulesGlobally` orders by occurrence instant then id — the reminder owed longest goes first — against a partial index on active schedules. Scanning globally is not writing globally: every row carries its own `organizationId`, read from the database rather than supplied, and every claim and finalization scopes itself by it. Owner-facing reads are unchanged and remain organization-scoped. Future multi-organization fairness is a change to that `ORDER BY` and `WHERE`; it requires no change to occurrence identity, which never mentions the scan that found it.

**Five-minute wake-up semantics, preserved.** `POST /api/v1/internal/reminders/process` suits an approximately five-minute external cadence, exactly as the Gmail poll and suggestion jobs do. Nothing repeats every five minutes: persisted occurrence instants are the scheduling authority and this endpoint asks which have arrived. A missed invocation is recovered by a later one, overlapping invocations are safe because occurrence identity is unique rather than because they do not overlap, and a backlog drains a bounded batch per cycle. No in-memory timer is load-bearing. **No cron job was created and no coordinator endpoint exists.**

**The endpoint is built dark, and has never been deployed.** An earlier A8.4a report described it as deployed, which was wrong in the only word that matters: the code was merged, and no deployment of any kind occurred. Bearer authorization with the existing cron secret, Node runtime, 60-second maximum, bounded batch, soft deadline, aggregate counters only, `Cache-Control: no-store` applied by a single response finalizer so no branch can forget it, no `GET` handler. With `ENABLE_REMINDER_DELIVERY` absent — which it is everywhere — it scans nothing, claims nothing, writes nothing, invokes no transport, and returns zero aggregates with `deliveryEnabled: false`. The flag is opt-in by exact string match: `"1"`, `"TRUE"`, `"yes"`, `"false"`, `"0"`, and `"true "` with a trailing space all leave delivery off, because the cost of guessing wrong is mail nobody approved.

The fake transport itself no longer defaults to acceptance: an unscripted one returns a permanent `transport_not_configured` failure. #### A8.4b.1 real Gmail overdue reminder delivery: implemented, awaiting architecture review

> **Status: implemented, not reviewed, not deployed.** This is the first of A8.4b's delivery slices. It substitutes a real Gmail transport for the fake one on the **overdue** path and changes nothing else about A8.4a. **Delivery remains disabled**: `ENABLE_REMINDER_DELIVERY` is set in no environment, and with it unset no Gmail transport is constructed at all. **No A8 migration is applied in Production, no reminder cron job exists, and this slice is not deployed — it sits in the unpushed local commits.** (A8 code through A8.4a _is_ deployed; see the incident notice at the top of this document.) **A8.4b.2 and A8.4b.3 are not implemented.**

**A8.4b.1 sends overdue reminders through Gmail, and nothing else changes.** Every A8.4a guarantee is intact and none was relaxed to make sending easier: organization-local due dates, IANA timezone resolution, one reminder per applicable local calendar day, no fixed 24-hour arithmetic, no backlog, generation semantics, Waiting behaviour, the D106 ceiling, idempotent claims, occurrence identity, two-phase finalization, the four recovery classes, and every source guard. The occurrence lifecycle did not learn that a provider exists.

**Gmail authorization is resolved once per invocation, before the first claim.** This is an ordering property, not a caching optimization. Resolving per occurrence would let an invocation claim ten occurrences, deliver three, and only then discover the connection was never usable — having consumed three of the Recipient's fourteen local calendar days on messages that had no chance of being sent. Resolving per schedule has the same shape at a smaller scale. So the abstract `ReminderTransportProvider` is resolved exactly once, and an unavailable result ends the invocation with **zero claims, zero occurrence rows, zero attempts, zero schedule mutations, and zero provider calls**, reported as `transportAuthorized: false`. **A Gmail authorization failure is never recorded as an occurrence-level reminder failure**: a missing connection is a fact about the deployment, and charging it to whichever Task the scan reached first would stop a schedule that did nothing wrong. The resolver itself is A7's `createGmailAccessResolver`, reused rather than reimplemented — a second authorization path would be a second place for refresh-token decryption and scope evaluation to disagree.

**The reminder transport is a dedicated adapter, and A7 is untouched.** It reuses the MIME builder, the raw Gmail sender, the HTTP-status classification, and the access resolver, and composes them directly rather than going through A7's `GmailTransport`. The reason is truthfulness: A7's transport takes an `OutboundMessage` whose `deliveryPath` is a `HandoffDeliveryPath` and echoes that value back on every acceptance, so reusing it would mean either widening an A7 domain type or recording a reminder as an `assignment_email`. The one shared change is that `buildMimeMessage` now takes `OutboundMimeMessage`, which is `OutboundMessage` **without** the `deliveryPath` it never read — a removed requirement rather than an added value, so every A7 call site compiles and behaves identically. No threading, no CC, no BCC, no new OAuth flow, no second token refresh, and no handoff send function is reachable from a reminder.

**D130 is enforced three ways, because one would not be enough.** The reminder carries no link: the builder has no field for one, every rendered line is URL-redacted, and both MIME bodies are asserted link-free before the message is emitted. The redaction matters because summary points are authorized content _derived from a real communication_ and can legitimately contain a URL — a value arriving from the database, which no amount of care at a call site would catch. A body that cannot be rendered safely produces a truthful non-retryable failure rather than a message that breaks the decision.

**Capability state is a pre-send gate, read from the same snapshot as everything else.** Because the reminder's only instruction is "use the original assignment email", the health of that email's capability is a precondition for sending at all. `readReminderPreSendSnapshot` now reads the canonical capability row inside the same `RepeatableRead` transaction as the Task, the assignment, the due date, and the schedule — five reads of one instant that existed. A second query after the fact would have reintroduced exactly the incoherent-read defect the A8.4a audit raised against the three-statement version of that function. When the capability is missing, expired, revoked, never activated by an accepted send, or already consumed, the occurrence is skipped as `no_actionable_capability`, **no provider call is made**, and it is not recorded as a transport failure. The skip is deliberately distinguishable from `no_active_assignment`: one means re-send the assignment, the other means assign somebody.

**Provider outcomes stay four-valued and truthful.** Confirmed acceptance carries the Gmail message id and nothing else — not the raw response, not `threadId`, not headers, not the MIME body, not the address. **A send failure that carries no HTTP status from Gmail is ambiguous, without exception** — a timeout, an unparseable response, a 2xx with no message id, and any connection failure. That last one was the re-audit's blocker: the raw sender reports every non-abort `fetch` rejection as a `network` failure, and Node raises the same rejection whether the connection was refused before the request was written or reset after Gmail received the entire body, so "network" cannot mean "not sent". Classifying it retryable left the occurrence owed and the schedule armed, and the next wake-up reclaimed the row — clearing the provider marker, as a retry takeover must — and sent a **second real reminder for the same local calendar day**. The marker is already committed when the failure is caught, so this is the same state a crash there would leave, and recovery finalizes that ambiguous; catching an error must not be less safe than crashing. The price is a provable pre-submission failure spending its occurrence's day instead of retrying, which is the direction every other trade here is resolved. Only Gmail answering with a status may produce a retry, because only that answer proves the message was rejected rather than kept: rate limits and provider unavailability are retryable, and invalid or oversized messages are permanent. Authorization refusals at send time are classified **retryable** rather than permanent — a deliberate departure from A7, where an Owner is present and "reconnect Gmail" is the useful answer; a worker with fourteen schedules in flight must not stop them all because a token aged out mid-run, and Gmail rejecting the request proves the message was not sent.

**D129 is recorded and deliberately not enforced in this slice.** Runtime enforcement of the three-consecutive-ambiguous threshold is A8.4b.2, below. What A8.4b.1 owes it is raw material, and what it provides is exactly that: every terminal ambiguous outcome is durable, dated, and attributable to a generation, so the count can be **derived** from history. **No ambiguous counter is stored, no new suspended state exists, and no schedule auto-resumes.**

**Real Gmail is unreachable from every automated test.** Four independent mechanisms: `lib/reminders` imports no provider and a directory-scanning guard fails the build if that changes; the route is the single composition point and is asserted to import exactly two Gmail seams; the flag is checked **in the composition root**, so with it unset no access resolver exists, no refresh token is decrypted, and no token exchange is attempted; and the adapter **throws** if asked to build the real sender under a test runner. The last one is the only protection that also covers tests nobody has written yet — a future test that forgets to inject a fake gets a loud error instead of an HTTP request to Google.

#### A8.4b.2 repeated ambiguous outcomes stop delivery: complete

> **Status: complete, committed locally at `c9a58fa`, not deployed.** A8.4b.1 is complete and committed locally at `7153bec`. **Delivery remains disabled**: `ENABLE_REMINDER_DELIVERY` is set in no environment, and with it unset no Gmail transport is constructed at all. **No A8 migration is applied in Production, no reminder cron job exists, and this slice is not deployed — it sits in the unpushed local commits.** (A8 code through A8.4a _is_ deployed; see the incident notice at the top of this document.)

**A8.4b.2 enforces D129 and changes nothing else.** Three **consecutive terminal ambiguous** overdue outcomes within one schedule generation stop that schedule: existing `stopped` status, new stop reason `repeated_ambiguous_outcomes`, `requiresOwnerAttention = true`. There is no new suspended state, no automatic resume, and no manual resume endpoint. Only a material Owner due-date change opens a new generation, and because the derivation is generation-scoped the new generation starts with no ambiguity history of its own — the reset is a property of the query, not an operation anybody has to remember to run.

**Why three, and why stop at all.** A8.4b.1 established that a send failure carrying no HTTP status from Gmail is ambiguous rather than retryable, because Node cannot distinguish a connection refused before the request was written from one reset after Gmail received the whole body. That is the right trade for one message — never resend something a provider may hold — but it has a consequence at the series level: a deployment whose path to the provider is broken produces one ambiguous occurrence every morning, each consuming a local calendar day under D106 and each leaving nobody able to say whether the Recipient heard anything. Without a stop, the system spends fourteen days of a Recipient's attention budget on messages that may not exist and reports nothing. Three is deliberately small: the cost of stopping early is an Owner glance, and the cost of stopping late is a Recipient who may or may not have been mailed a dozen times.

**What counts, and what does not.** The unit is the **final occurrence outcome**, never a raw provider attempt — one occurrence retried three times is one outcome, and counting attempts would stop a schedule that had seen a single uncertain morning. A confirmed **success breaks** the run, because a message that provably arrived says the path works. A **permanent failure breaks** it, because it is a definite answer; that includes retry-budget exhaustion, which the worker records as a permanent failure and which is counted as the permanent failure it was recorded as, never re-read as ambiguity because earlier attempts were uncertain. A **skip neither counts nor breaks** the run: no provider was contacted, so it says nothing either way, and a schedule that skips a fortnight between two ambiguous mornings has still seen two consecutive ambiguous _deliveries_. A **retryable or still-claimed** occurrence is invisible until it finishes, because the occurrence may yet be delivered and judging it early would judge an outcome the generation has not reached.

**No counter exists, anywhere.** The stored-count implementation is the obvious one and the wrong one: it has to be incremented on ambiguity and reset on success, on permanent failure, and on a new generation, and any path that forgets one leaves a schedule that stops early or never stops. The answer is derived instead, from the append-only occurrence rows that are already authoritative. A schema guard asserts no ambiguity column exists and that the status enum still has exactly three values.

**Where it is enforced, and why there.** At the occurrence-to-schedule settlement boundary — the same transaction that already holds the Task lock, already applies the schedule effect exactly once, and already evaluates the D106 ceiling the same way. That placement gives four properties for free: the occurrence is already terminal when the threshold is judged, the read cannot be stale because the lock is held, a crash between finalization and settlement is repaired by the existing unsettled-occurrence sweep, and re-settling an occurrence is a no-op because settlement is already idempotent. No provider adapter decides it, no worker decides it, and nothing scans history outside the transaction and then mutates from what it found.

**The history read is bounded and ordered by occurrence, not by clock.** Three rows, filtered in SQL to the outcomes that participate, scoped to the schedule's current generation, ordered by scheduled `occurrence_at` with the row id as tie-breaker. Ordering by `completed_at` would have been the tempting choice and is wrong in a specific way: settlement can be late — a crashed occurrence swept hours afterwards, or recovery collecting debt out of order — and ordering by when work finished would make the repair of an old occurrence look like the newest event in the sequence.

**Precedence with the other stops.** Every stop in the settlement path is conditional on the schedule still being `active`, and D129's is no exception, so an earlier authoritative transition keeps the reason it recorded: a Task the Owner completed stays `task_completed` even if a third ambiguity settles afterwards. The occurrence is still recorded truthfully as ambiguous — D129 changes the schedule, never the occurrence. The ceiling cannot conflict, because it arises only from a success and a success breaks the run.

**No fourth reminder.** The stop nulls the armed occurrence, and the due scan selects on exactly that, so a stopped schedule is invisible to the invocation that stopped it, to a concurrent worker, and to the next wake-up. The A8.4a pre-send guard is the second line: it re-reads the schedule inside the occurrence transaction and refuses one that is not `active` and armed, which is what defeats a candidate a worker pre-fetched before the stop committed.

#### A8.4b.3 advance reminder delivery: implemented, awaiting architecture review

> **Status: implemented, not reviewed, not deployed.** A8.4b.1 and A8.4b.2 are complete and committed locally at `7153bec` and `c9a58fa`. **Delivery remains disabled**: `ENABLE_REMINDER_DELIVERY` is set in no environment, and with it unset no Gmail transport is constructed at all. **No A8 migration is applied in Production, no reminder cron job exists, and this slice is not deployed — it sits in the unpushed local commits.** (A8 code through A8.4a _is_ deployed; see the incident notice at the top of this document.)

**A8.4b.3 makes the one advance reminder deliverable and changes nothing else.** D105 has specified it since A8.0 — one reminder, 09:00 organization-local on the calendar day before the due date, only while the Task is actionable — and A8.3a has persisted it since: every generation stores its advance instant, its local date, and a disposition. What was missing was a query. The worker's due scan selected on `next_overdue_occurrence_at`, so an advance occurrence could be established, skipped at establishment, and skipped by a Waiting period, but never claimed and never sent. This slice adds the scan, the index that makes it cheap, and the one rule delivery needs that establishment did not.

**Two scans rather than one wider one.** Overdue follows a rolling pointer re-armed after every occurrence, so a schedule reappears in it daily. Advance reads one immutable instant per generation, gated on `advance_disposition = 'scheduled'`, a value that settles exactly once and never returns. A merged query would not be able to report which occurrence it had found, and a merged index would serve neither ordering. So there are two bounded scans, each with its own partial index, feeding one claim-guard-send-settle pipeline — occurrence identity already includes the kind, so everything downstream of "which occurrence" was already kind-agnostic. Advance is processed first: it is the older instant whenever both are due, which needs an outage long enough for the due date itself to pass.

**The disposition is the whole of the "not yet handled" test.** The scan needs no anti-join against occurrence history, because every terminal outcome settles the disposition inside the same transaction that marks the occurrence settled. Delivered, skipped, failed, and ambiguous advance occurrences have all left the scan before the next invocation runs, and so have the two skips that happen without a worker — the window having already elapsed at establishment, and a Waiting period having spanned the morning. This is also why the index is partial on the disposition as well as on `active`: it stays proportional to work outstanding rather than to history.

**How late is too late, and why it is a calendar question.** An overdue occurrence stays owed however late the worker is; the Task is still late, so the nudge is still true. The advance reminder cannot be late at all, because its content is that the Task is due tomorrow, and a worker reaching it the next morning would state something false about a Task due today. The gate is therefore a **calendar-day comparison in the organization's zone**: deliverable at any point during the local day before the due date, never afterwards. A lateness budget measured in hours would be wrong twice a year — the advance day is 23 or 25 hours long in the weeks the clocks shift, so a fixed 24 would either cut an hour off that day or spill an hour past midnight into the due date. `isAdvanceDeliveryWindowOpen` lives in the domain beside `decideAdvanceReminder`, and a guard fails the build if the worker starts doing hour arithmetic instead of asking it.

**A missed morning is claimed, not filtered.** A worker reaching an advance occurrence after its day has ended still claims it, makes no provider call, and settles it as `advance_window_elapsed` — the same fact establishment records for a schedule created too late to have an advance morning at all. Filtering those rows out of the scan would have been simpler and would have left them saying `scheduled` for good, with nothing remaining in the system that would ever correct them. The settlement distinguishes that skip from `skipped_not_eligible`, which is the only behavioural change this slice makes to an existing path: an outage and a completed Task both produce a skipped advance occurrence, the Owner's remedy differs between them, and collapsing both into "not eligible" would put them in the same bucket on the one surface that answers what happened.

**The message does not change.** D105 makes the advance reminder a difference in timing, not in content. The approved body states the due date and instructs the Recipient to use the original assignment email; it never asserts that anything is late, so it is truthful the morning before and every morning after. No new wording, no escalation language, no "due tomorrow", no capability link (D130), no counts, no schedule identifiers. A8.4b.1's adapter refused any occurrence kind but `overdue` precisely so that an advance scan arriving before the content rules could not start sending silently; that refusal is now removed, and two guards replace it — one asserting the two kinds produce byte-identical MIME, one keeping `occurrenceKind` out of the email module entirely.

**Waiting, generations, and eligibility are unchanged and were not re-decided.** A Waiting schedule is not `active`, so it never enters the scan; a resume that lands past the morning has already had its disposition settled to `skipped_waiting_elapsed` by the existing lifecycle path, which takes it out of the scan permanently. A material due-date change opens a new generation with a freshly derived advance occurrence, and the superseded one disappears with the generation it belonged to — the pre-send guard's generation check is what stops a worker holding a stale candidate from sending it. Completion, dismissal, due-date removal, a cleared assignment, and a non-actionable capability (D130) all skip through the same guards the overdue path uses.

**D129 was deliberately not extended.** The rule counts three _consecutive_ terminal ambiguous outcomes, and a generation holds exactly one advance occurrence, so an advance ambiguity can never be the second or third of anything — extending the rule would not make it stop earlier or later, it would make it count a sequence that cannot exist. The SQL filter and the domain predicate each say `overdue` independently, the advance settlement branch returns before the D129 block is reachable, and guards assert all three. Advance occurrences likewise do not count toward D106's fourteen successful overdue deliveries, which was already true and is now reachable.

**Evidence.** `apps/web/__tests__/a8-4b3-advance-delivery.test.ts` (sent once on its morning; not before its instant; never twice; the occurrence, disposition, and provider reference recorded; not counted toward D106; the overdue series unaffected afterwards; still sent at 23:55 on the advance day; refused on the due date with `advance_window_elapsed` and no provider call; settled so it never returns; the spring-forward 23-hour day closing at local midnight rather than 24 hours later; Waiting suppressing it, a resume past the morning leaving no backlog, and a resume before the morning still sending; due dates moved later, moved earlier, removed, and restored; a delivered advance surviving a generation change without resending; completed, dismissed, unassigned, and revoked-capability skips; an ambiguous advance not reaching D129; a permanent advance failure not stopping the overdue series; nothing at all with the flag unset; and both occurrences settled truthfully after a long outage), `packages/db/__tests__/a8-4b3-advance-scan.test.ts` (every way a row leaves the scan — early, settled to each of six dispositions, Waiting, stopped — plus row shape, instant ordering, batch bounding, limit validation, disjointness from the overdue scan, each terminal outcome's disposition including the window-elapsed distinction, and the migration file's additive one-statement shape), and the A8.4b.3 guards in `a8-4a-worker-safety-guards.test.ts` (one transport call site, one claim call site keyed by the candidate rather than a literal, the provider marker still committed before the send, the window rule delegated to the domain with no hour arithmetic, the email builder free of `occurrenceKind`, and D129 unreachable from the advance branch).

#### A8.4a audit remediation: recovery and settlement safety

The critical worker-safety audit of `cfb733b4` found two Blockers and three High findings and refused the slice as a delivery foundation. All five are closed. None was a bug in the happy path; every one was a way for the system to be **silently wrong after a crash**, which is exactly what a worker-safety foundation exists to prevent.

**B1 — recovery disarmed the schedule it was recovering.** `finalizeAbandonedInFlightOccurrence` finalized the occurrence `ambiguous`, correctly, and then passed no next occurrence to settlement. Settlement wrote that null faithfully: `next_overdue_occurrence_at = NULL` on a schedule still `active`, with no stop reason and no Owner attention. The series simply ended, and nothing recorded that it had — no error, no attention flag, no row to find. The recovery path now computes the next occurrence with the same `selectNextOverdueOccurrence` call the live path uses, and arms it while the schedule is still active at the matching generation. The invariant is asserted in **both** directions now: a non-active schedule holds no armed occurrence, and an active schedule holds one. The second half is new, and it is the half B1 violated.

**B2 — an exhausted retry budget was a permanent hot loop.** A worker that died on its last permitted attempt _before_ marking a provider call left an occurrence that was non-terminal, at the attempt ceiling, and had no live lease once recovery released it. The claim path refused it with `retry_budget_exhausted`; the schedule stayed active and armed at an instant already past; and every subsequent invocation scanned it, tried to claim it, was refused, released the lease, and repeated — for as long as the deployment lived. `terminalizeExhaustedRetryOccurrence` now closes it as a `permanent_failure` carrying `retry_budget_exhausted`, and settlement applies the ordinary permanent-failure policy, which stops the schedule, raises Owner attention, and removes it from the scan. A second worker meeting the same row sees the terminal outcome and does nothing.

**H1 — an unexpected settlement failure erased a recorded delivery.** Covered in the F1 correction above. Terminalization and settlement are two transactions, `schedule_settled_at` is the durable seam, and a sweep discharges the debt on the next invocation without going near a transport.

**H2 — a retry inherited the previous attempt's provider marker.** Taking over a `retryable_failure` row kept `provider_call_started_at` from the attempt that failed. So a retry that crashed before reaching its _own_ transport call looked in-flight to recovery, which concluded a provider might hold the message and finalized it `ambiguous` — a reminder provably never sent, recorded as probably delivered, its local day consumed. Takeover now clears the marker, the acceptance fields, the message reference, and the settlement marker, and a CHECK refuses a settled row that is claimed again.

**H3 — the fake transport defaulted to accepted.** Nothing in production constructed one, but the default was the wrong shape for a safety foundation: one environment variable away from a system recording deliveries it never made and burning the D106 ceiling on them. Processing now requires an injected transport and does no work without one, and an unscripted fake returns a permanent `transport_not_configured` failure rather than acceptance.

**Also folded in, because they are the same wound.** Recovery debt is discharged before new work, each class bounded on its own budget so one unprocessable row cannot starve the scan. The pre-send guard reads Task, assignment, due date, and schedule in **one** `RepeatableRead` snapshot instead of three independent statements. `Cache-Control: no-store` is applied by one response finalizer. The aggregate gained counters for claim refusals, retry-budget terminalizations, settlement debt collected, settlements deferred, and whether the soft deadline stopped the run.

**Schema.** One additive migration, `20260802094500_a8_4a_settlement_marker`: a nullable `schedule_settled_at`, a backfill marking all pre-existing terminal rows settled (true by construction — they were written under the single-transaction design), a CHECK added `NOT VALID` then validated, and two partial indexes for the settlement-debt and retry-budget sweeps. Tested from empty and over the predecessor migration with representative rows including every legacy half-written claim shape the predecessor schema permitted. **Not applied to Production.** Its header also corrects the previous migration's false claim to backfill nothing; the correction is recorded in the new file rather than by editing the applied one, because Prisma checksums applied migrations and editing one breaks `migrate deploy` on every database that already has it.

**Still absent after the remediation:** no Gmail or other real provider, no capability-link storage, no advance delivery, no Event Notification, no cron job, no production enablement, no UI, no deployment, and no production migration.

#### A8.5b claim semantics, worker state machine, and fake transport: implemented, awaiting architecture review

> **Status: implemented, not reviewed, not deployed.** Delivery is disabled: `ENABLE_OWNER_EVENT_DELIVERY` is set in no environment, and the route supplies no transport in any environment, so either condition alone reduces an invocation to a zero-work response before a database connection is opened. **The only transport is a fail-closed fake that exists for tests. **A8.5b makes the A8.5a state machine reachable and stops short of anything that could send.** A worker route, a claim protocol with leases and fencing, the full set of terminal outcomes, expired-claim recovery, staleness suppression, and a transport seam whose only implementation refuses to succeed. **No migration.** The A8.5a schema was designed for this slice and the twelve CHECK constraints turned out to be the specification: every transition below is shaped by what the database would already have refused.

**`failed_retryable` is a state the intent row never rests in, and that is deliberate.** A retryable failure returns the intent to `pending` and clears its lease, because the worker scan is served by `owner_notification_intents_pending_idx`, a partial index on `state = 'pending'`. Resting retries in their own state would put half the eligible work outside the index the scan depends on, and would need either a second index or a scan that stops using the first. The retryable outcome is not lost by doing this — it is recorded on the append-only attempt row, which is where per-attempt history belongs. `requires_owner_attention` is reserved for the terminal outcomes that need a human: retry exhaustion, permanent failure, and ambiguity.

**The order of operations is the entire crash-safety argument.** Claim and commit; record that a provider call is starting and commit that; call the transport with **no transaction open**; settle in one transaction fenced on the claim's token. An attempt row left `in_flight` by a dead worker is durable evidence that a provider was contacted and the answer is unknown — which is the definition of ambiguous. Without that marker, a worker that died mid-call would be indistinguishable from one that died before calling, and recovery would have to choose between never delivering and delivering twice. Recovery therefore does not guess: `recoverExpiredOwnerNotificationClaim` decides atomically, releasing the lease back to `pending` when no attempt began and returning the in-flight attempt for ambiguous terminalization when one did. **A lapsed lease after provider contact is never retried.**

**Claiming is compare-and-set on a fencing sequence, following A8.4a rather than inventing a second pattern.** `updateMany` with the observed `claimSequence` in the predicate and an incremented one in the update; the affected-row count is the answer, and the loser is told it lost rather than discovering it later. The token is then carried into every subsequent write, so a worker whose lease was superseded while it was calling a provider cannot settle: its predicate no longer matches. Nothing depends on an in-memory lock, a process-local map, scheduler serialization, or a single instance.

**Beginning an attempt is a second compare-and-set, which the PostgreSQL suite is what caught.** Fencing on `claimSequence` alone is not enough: two calls under one valid claim would each increment `attempt_count` and each insert an attempt row, and the concurrency test found exactly that with three workers. `beginOwnerNotificationAttempt` now also asserts the `attempt_count` it expects to advance from, so the increment and the attempt insert are one atomic step that exactly one caller can win. Attempt numbering is a consequence of that compare-and-set rather than of a read followed by a write.

**One-shot policy, and the refusal to inherit reminder policy is the point (D135).** Three total attempts; retryable failures consume budget and exhaustion is terminal and needs the Owner. Ambiguity is terminal on the **first** occurrence, is never retried, and is never counted as sent — D129's three-consecutive-ambiguity rule is a property of a repeating reminder series and an Owner event notification is not one. D106's fourteen-delivery ceiling, reminder generations, daily occurrence rules, Waiting suspension, and reminder schedule settlement are all absent for the same reason. A transport that throws is classified ambiguous rather than retryable, because the in-flight marker is already durable and the throw may have happened after the request left.

**Staleness is checked before anything is claimed and terminalizes without pretending contact occurred.** An intent older than twenty-four hours at processing time is suppressed with a durable reason and settlement instant, makes zero transport calls, creates **no attempt row**, and is never eligible again. That last property is what stops a backlog accumulated while delivery was disabled from flushing the day somebody enables the flag. The comparison uses instants passed in from the caller; `packages/db` still reads no clock.

**Terminal outcomes get audit events in A8.5b rather than A8.5c, because they can be truthful without knowing a provider exists.** D133 requires them, and the test is whether the taxonomy forces a Gmail assumption — it does not: `sent`, `failed_permanent`, `ambiguous`, `retry_exhausted`, and `suppressed_stale` are statements about Rocket's own workflow. Attribution is `system` and only `system`; the intent keeps the triggering actor, and copying it here would say a Recipient sent the Owner an email. `suppressed_stale` maps to `denied` rather than `failed`, the only one of the three outcomes that does not assert an error the system never encountered. The audit row is written **in the settlement transaction**, so a terminal state and its audit event commit together or neither does. Attempt rows remain the operational source of truth; the two records are not merged.

**The fake transport is fail-closed, which matters more than what it can simulate.** An unscripted call returns a permanent failure rather than success, so a test that forgets to script an outcome fails loudly instead of quietly asserting a delivery that never happened. The route constructs **no** transport, and the service treats an absent transport exactly as a disabled flag: zero work, no claim, no database access. A fake cannot become reachable in production by being the default, because there is no default. The seam carries identity — intent, organization, event type, subject, attempt number — and no address and no content, so A8.5c can implement it without widening it.

**Delivery gating is control flow, not a promise.** `ENABLE_OWNER_EVENT_DELIVERY` is exact-string `"true"`, read before `loadDbRuntime`, so a disabled invocation opens no connection at all rather than opening one and declining to use it. `1`, `TRUE`, `yes`, and whitespace variants stay off. The endpoint is `POST /api/v1/internal/notifications/process` — POST only, `Authorization: Bearer <CRON_SECRET>` through the existing `authorizeCronRequest`, Node.js runtime, `maxDuration = 60`. Its constants are the reminder worker's proven values rather than new ones: twenty-five per invocation, a two-minute lease, a fifteen-second deadline reserve. The reminder route is untouched and the two workers stay separate endpoints.

**The aggregate response is contracted.** The repository already contracts the reminder worker's response, so this one follows: counts and flags only, every field required, no address, Task summary, actor label, event subject, or provider payload. `batchFilled` reports that the scan filled its batch rather than counting what remains, because an exact remainder needs an unbounded `COUNT` over every pending row and an aggregate should not promise something that expensive.

Recipient note bodies, clarification text, and Gmail excerpts have no parameter to arrive through — the prohibition is semantic, and escaping does not satisfy it, because a Recipient's words in the Owner's inbox under Rocket's `From` address is laundering regardless of how they are encoded.

**Attribution is the historical fact, read from the intent.** A Recipient completion renders as "the recipient, using the link you sent them" — never "you completed", never "Rocket completed". It comes from the intent row rather than from current Task state, because a Task completed by a Recipient and later reopened by the Owner is still a Recipient completion and today's row would say otherwise. The label is the actor _kind_ and nothing finer; no Recipient name or address appears.

**The link is permitted here for the reason D130 forbade it there (D134).** D130's subject is the capability bearer secret. An Owner is not a bearer: `/tasks/{id}` on the application's own origin is not a credential, and following it without a session reaches sign-in rather than Task data. The base URL goes through the same validator capability URLs use, the identifier is path-encoded, and the renderer refuses any body containing a `/c/` path or any URL other than the one it chose — which is what catches a summary point whose redaction pass was skipped.

**The marker is one header the caller cannot forge or repeat (D136).** `OutboundMimeMessage` gained a single optional field from a closed union; the MIME builder owns the header name, validates the value, and pushes it exactly once. "Callers cannot supply arbitrary headers" therefore survives the addition, which matters because that property is what makes header injection unreachable rather than merely unlikely. Assignment emails, Gmail forwards, and Recipient reminders are byte-identical to before and structurally unable to set it.

**The ingestion exclusion is narrow, and ambiguity denies it.** Gmail files a send-to-self notification under both `SENT` and `INBOX`, so D068 would admit it and A6 would offer the Owner a suggestion derived from Rocket's own mail. The sync engine now skips a message carrying exactly one `X-Rocket-Generated: owner-event-notification`, **before** the fixture is built — so no excerpt is created and no `CommunicationEvent` exists for A6 to claim. **No Gmail API change was required:** the poll already fetches `format=full` with `payload(headers(name,value))`, so the header was available and only needed reading. Only top-level headers are consulted, because honouring a nested `message/rfc822` part's headers would let anyone claim the exclusion by attaching a forwarded copy of one of Rocket's. Two markers, an empty value, or a near-miss token all fail closed and stay ingestible; Rocket's builder can emit none of those shapes. Ordinary self-sent mail, `SENT` plus `INBOX` mail, mail from the connected address, assignment emails, and reminders all remain eligible under the unchanged D068 rules.

**Provider classification is A8.5c's own, not the reminder worker's.** A confirmed message id is `accepted` and only the short reference is kept. A 2xx without one is `ambiguous`, never `sent`. Timeouts, unparseable responses, and every thrown error are `ambiguous`, preserving A8.5b's contract that a crash and a caught error at the same instant produce the same answer. 401 and 403 are `retryable` — Gmail proved it did not accept the message, and the next invocation resolves a fresh token. A **disconnected or unscoped account is `permanent`**, decided before any Gmail contact and before the Task is even read: the reminder worker can treat this as retryable because it resolves authorization before its first claim and simply ends the invocation, while this worker has already claimed the intent and must answer for it, and three attempts against a mailbox nobody has reconnected is not worth the Owner's attention twice. **The existing A8.5b outcome vocabulary was sufficient — no `channel_unavailable` was needed**, because `permanent` already means terminal, unsent, and requiring Owner attention.

**Nothing about the destination is persisted or logged.** No intent row, attempt row, audit event, log line, worker response, or failure code carries an address. Failure codes come from a closed set defined in code; a provider body or exception string cannot reach one.

#### A8.5d Complete event coverage and capability-expiry observation: implemented, awaiting architecture review

**All ten ratified event types now have a durable producer, and none of them can send anything.** The nine that were missing are written from the transaction that establishes the event they describe, `ENABLE_OWNER_EVENT_CAPTURE` is unset in every environment, and `ENABLE_OWNER_EVENT_DELIVERY` is still unset too. **No migration:** A8.5d adds no column, no table, no index, and no enum value. The A8.5a schema turned out to be the specification for all ten events, not just for the first.

**Every producer sits inside an existing transaction rather than beside one.** A clarification request and a return to Owner join the A4 unit of work that already commits the Task mutation and its audit row. A terminal handoff failure joins the A7 transaction that records it. A reminder stop joins the A8.4b settlement that applies it. A capability expiry gets a transaction of its own, because it did not have one. In every case the triggering state change, the audit event, and the intent commit together or none of them do — nothing polls the audit log, nothing enqueues after a commit, and a rolled-back mutation leaves nothing behind.

**Capability expiry was the one event with no chokepoint, and now has one.** `expiresAt` passing is not a write, so an untouched capability stayed `active` indefinitely while every reader treated it as expired — an event nobody recorded is an event nobody can be told about. `observeCapabilityExpiry` is now the single durable transition: a compare-and-set on `status = 'active' AND expiresAt <= at`, then the audit row and the intent, written only by the caller whose update won. The lazy path that already persisted expiry when a Recipient presented a lapsed token was rewired to call it, so a Recipient's click racing a sweep produces **one** transition, **one** audit event, and **one** intent rather than two of each. A loser writes nothing at all, because there is no such thing as a harmless duplicate audit row.

**The sweep is implemented and deliberately unwired.** `runCapabilityExpirySweep` finds expirable capabilities in a bounded batch and observes each one, and nothing calls it. Wiring it into the A8.5b worker route would have meant one of two things, and neither is A8.5d's to decide: either the route opens a database connection while `ENABLE_OWNER_EVENT_DELIVERY` is unset — destroying the "delivery disabled means zero database access" guarantee A8.5b documented and a guard enforces — or the contracted worker response grows fields describing sweep work. The transaction and its concurrency proofs are the expensive, dangerous part and they are done. **Documentation must not claim expiry is swept, because no scheduler and no worker invokes it.** _(A8.5e took the second option deliberately, replacing the A8.5b invariant with a stronger one and growing the response additively. The sweep is wired behind `ENABLE_OWNER_EVENT_CAPTURE` as of A8.5e; still nothing **schedules** it.)_

**Attribution is the actor of the event, not the actor of the request.** Six of the ten are observations rather than actions, and all six are `system`-attributed with an identifier naming the subsystem that observed them. This is not cosmetic. The A7 audit for a handoff _request_ is Owner-attributed and truthfully so, but a provider refusing the message is not something the Owner did; an Owner pressing "sync now" is how a lapsed Google grant gets noticed, not how it lapsed. Copying the request's actor onto the event would render as "Who acted: you" on an email telling the Owner their mail connection died.

**`gmail.disconnected` needed the status write to become compare-and-set.** The repository wrote `needs_reauth` unconditionally, which was fine when a failing sync was its only caller and the engine had already refused to run on a degraded account. It is not fine as a notification trigger: "the channel went down" is an event about a _transition_, and an unconditional write cannot tell a transition from a re-observation. Requiring `status = 'connected'` makes one notification per outage a property of the row, and a second observer writes nothing — no status change, no audit row, no intent — and is told so.

**`reminder.no_active_assignment` fires only when the Owner genuinely has something to do.** Decided in the settlement transaction, under the Task lock it already holds, from three durable facts: the skip reason is exactly `no_active_assignment`, the schedule is still active at this generation, and nobody is assigned _now_. A gap closed between the skip and its settlement produces nothing. What is deliberately not attempted is distinguishing a ten-minute Recipient swap from a schedule abandoned for a week — no durable "unassigned since" state exists, and inventing one to soften a notification would be persisting mutable state for prose. The generation-scoped identity already bounds the cost of that ambiguity to one message per generation.

**One real defect found and fixed while wiring the reminder events.** The first mapping from settlement effect to stop event read `scheduleAdvanced` for a permanent failure. That flag means "this settlement stopped an active schedule" on an overdue occurrence and something else entirely on an advance one — that a disposition was recorded on a schedule still running. An advance reminder that failed permanently would have announced a stop that never happened. The mapping now requires the occurrence kind as well.

**No reminder decision changed.** D106's ceiling, D129's ambiguity evaluation, settlement ordering, delivery counts, attempt outcomes, stop semantics, and A8.4b's claim behaviour are byte-identical; capture is an extra row written beside the settlement, and a guard fails if a reminder branch ever reads it. Settlement with capture off is the settlement A8.4b already performed.

**Renderer truthfulness was assessed per event before any producer was written, and no event required new persisted data.** Six are truthful and sufficient. Four are truthful but intentionally generic — a handoff failure names no provider reason, a clarification request quotes no question, a Gmail disconnection names no error code, a reminder stop names no failure. All four point the Owner at the surface where the detail lives, which is the whole design: the notification says an event happened, and the authenticated app says what it was. **None was materially misleading, so nothing justified widening A8.5a storage.** One addition was needed to keep that true: six of the ten events are about a schedule, a capability, or a handoff attempt rather than a Task, so an indexed subject-to-Task lookup now runs at render time and the email names the work. It selects an identifier and nothing else.

#### A8.5e Operational gating and milestone readiness: implemented, awaiting architecture review

**A8.5 is now complete as an implemented, validated, and wholly inert subsystem.** The last missing wire — something that invokes capability-expiry observation without a Recipient clicking a dead link — is in place, both flags remain unset in every environment, and no cron job exists to call the endpoint even if they were set.

**The endpoint has two phases, and they are gated separately because they are separate decisions.** `POST /api/v1/internal/notifications/process` now runs a **capture** phase under `ENABLE_OWNER_EVENT_CAPTURE` and a **delivery** phase under `ENABLE_OWNER_EVENT_DELIVERY`. Capture observes expiry, writes audit rows and intents, and contacts nothing. Delivery is A8.5b and A8.5c, unchanged: claim, fence, in-flight marker, provider call outside every transaction, settle. No transaction spans the two, and neither reads the other's flag.

| `ENABLE_OWNER_EVENT_CAPTURE` | `ENABLE_OWNER_EVENT_DELIVERY` | Behaviour                                                                                              |
| ---------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| off                          | off                           | No database access, no transport, no work — **today's state in every environment**                     |
| on                           | off                           | Bounded expiry observation only; no transport composed, no intent claimed, no Gmail configuration read |
| off                          | on                            | Delivery only; no expiry scan, and no new `capability.expired` intent can appear                       |
| on                           | on                            | Expiry observation, then delivery, sharing one deadline                                                |

Each flag is exact-string `"true"` independently, so `"1"`, `"TRUE"`, `"yes"`, and a stray space leave that flag off without affecting the other. `ENABLE_REMINDER_DELIVERY` is unset, independent, and not read by this endpoint at all.

**A8.5b's zero-database-access invariant was replaced deliberately, not deleted.** A8.5b promised that _delivery disabled means zero database access_, which was true of an endpoint whose only work was delivery. Keeping it would have meant refusing to observe expiry unless mail was already flowing — inverting the enablement order the whole milestone is built around. The replacement is **both flags off means zero database access and no transport**, and at the point that matters it is strictly stronger: it now covers the route, which under A8.5b constructed a Prisma client before it read anything. The route passes `getDb` as a thunk rather than awaiting it, so "opened no connection" is an observation a test makes rather than an inference from where a flag is read.

**Failure isolation is a consequence of the phases sharing no transaction.** A lost expiry race is counted, not raised — another observer got there first and this one wrote nothing. A systemic scan failure aborts the invocation and returns a truthful `500`, leaving already-committed transitions committed. An invalid Gmail configuration after a successful capture yields `transportConfigured: false` and rolls back no expiry. Running out of budget during capture stops the invocation before any transport is composed, so no credential is touched on the way to doing nothing; the observed expiries are durable and the next invocation finds their intents.

**Capability authorization truth never depended on any of this, and still does not.** An expired capability is unusable whether or not its notification was delivered, whether or not capture is enabled, and whether or not the sweep ran — the validator's own expiry rule is unchanged. The sweep makes the transition _durable_; it does not create it. A capture-disabled sweep performs the transition and writes the audit row with no intent at all, which is the shape of the proof: notification-intent uniqueness is not an authorization condition.

**The expiry scan is bounded, deterministic, and deliberately unindexed.** Fifty capabilities per invocation, ordered by earliest `expiresAt` with an identifier tie-breaker, with the batch size validated inside `packages/db` so a caller cannot widen it. The scan is global across organizations — expiry is a property of the clock, not of a tenant — which means the existing `(organization_id, status, expires_at)` index cannot serve it, and PostgreSQL 16 plans a sequential scan with a top-N heapsort. Measured on a seeded table of 9,109 rows: **0.74 ms, 362 shared buffer hits**. A capability row is written once per handoff, so the table grows with delivery history rather than with traffic, and that cost is far inside a five-minute worker's budget. **No migration was added.** The remedy if it ever matters — a partial `(expires_at, id) WHERE status = 'active'` index — is recorded in the planner test rather than applied on speculation.

**The worker response grew six additive fields**: `captureEnabled`, `expiryScanned`, `expiryObserved`, `expiryLostRaces`, `expiryBatchFilled`, and `expiryDeadlineStopped`. Every existing field kept its name and meaning; `deadlineStopped` was already invocation-level and is now true if either phase stopped, with `expiryDeadlineStopped` distinguishing which. Counts and booleans only — no capability identifier, address, expiry instant, or provider content. OpenAPI, the TypeScript schema, and the Kotlin model were regenerated and the drift check passes.

#### A8.6a Attention surface: implemented, awaiting architecture review

**`/attention` reads.** It is now the **cross-Task discovery surface** D108 requires: the place an Owner learns that reminder automation has stopped without inspecting Tasks one at a time. Until now it was the P1.4 placeholder — authenticated, deliberately empty, and honest about reading nothing.

**Why a Task page could not have been enough.** D108 conditions enabling Recipient reminder delivery on the Owner being able to see the state of the automation acting for them. Per-Task status answers "what happened to this Task" for an Owner who already suspects which Task to open. It cannot answer "did anything stop", which is the question a stopped schedule needs asked of it, because the Owner has no reason to go looking. That is a cross-Task question and it needs a cross-Task surface.

**What was added.** One repository function, `listReminderSchedulesRequiringOwnerAttention`, reading schedules where `requires_owner_attention` is true; one Owner-facing projection; a server component rendering it; and its loading and error boundaries. **No endpoint, no mutation, no persistence, and no migration.** The existing `@@index([organization_id, requires_owner_attention])` — added by A8.3a and until now unread by any repository function — serves it.

**Three properties of the read carry the weight.**

_Bounded._ Fifty per load, validated inside `packages/db` so a caller cannot widen it, and a filled batch is disclosed to the Owner rather than silently truncated. An Owner-facing read whose cost scales with how badly things have gone gets slowest exactly when it matters most.

_Organization-scoped on both sides of the join._ The schedule filter is application-level because deny-by-default RLS with no policies is not tenant isolation for a Prisma read whose connection role owns the tables. The Task filter is application-level for a different reason: **no composite foreign key binds a schedule's organization to its Task's**, so their agreement is an invariant the write path maintains rather than a fact the database enforces. Asserting it in the `where` makes a cross-organization Task unmatchable in SQL, and the row drops out entirely. Hidden rather than leaked is the correct direction — a missing attention item is recoverable, a link to another organization's work is not.

_Constant round-trips._ Two statements — one for the schedules, one batched relation load for their Tasks — measured at the driver and asserted **flat** from one row to six. Flatness is the assertion that matters; the absolute number is bracketed at one or two because it is a Prisma relation-loading strategy that may change without this query changing.

**Two traps were specifically guarded, because neither would fail a type check or look wrong in review.** `Task.reminder` is the A2-era `ReminderMetadata` blob — `nextReminderAt`, `paused`, `pausedReason` — which still sits on every Task row, reads exactly like what this surface wants, and has not been maintained since A2; a page displaying its `nextReminderAt` would state a next reminder date no scheduler wrote. And the reminder **ETag is not a freshness signal**: it deliberately does not move when a worker records a delivery, increments the overdue count, or raises the attention flag, so an attention item can appear while it is unchanged. Source guards prohibit both.

**A third trap was found while building it.** A due date is a `YYYY-MM-DD` calendar date already in the organization's zone, not an instant. Passing it through the existing instant formatter parses it as UTC midnight and renders the previous day in `America/Vancouver` — an Owner shown a deadline one day earlier than the one they saved. `formatOwnerLocalDate` parses and formats in UTC so the two conversions cancel, and refuses a full ISO instant rather than coercing it.

**The copy is the product.** Three stop reasons raise attention — `overdue_ceiling_reached`, `permanent_delivery_failure`, `repeated_ambiguous_outcomes` — and each gets a specific sentence. The ambiguity wording preserves D129's distinction exactly: Rocket **could not confirm** delivery and the Recipient may or may not have received it, which is not the same as knowing it was missed. The other three stop reasons and a null are mapped to a truthful generic sentence rather than to an invented fourth attention reason, so a state the write path does not produce still renders something true. No `generation`, claim, lease, or row identifier reaches the projection type.

**Empty, loading, and error are three different messages, and the error state matters most.** A failed attention read means Rocket **cannot say** whether automation has stopped. Rendering the empty state instead would report "nothing needs your attention" on the strength of a missing table, so the boundary refuses that reading in as many words and the page lets database failures propagate. `/attention` now depends on the **A8.3a migration chain, which is not applied in production**, and a deployment reaching it without those tables is supposed to break visibly.

**One contract correction, description-only.** The `GET /api/v1/tasks/{taskId}/reminder` description still said `overdueDeliveredCount` is always 0 because nothing schedules, claims, sends, or retries a reminder. A8.4b made that false — the worker exists and counts. The field is 0 in every deployed environment because delivery is **disabled**, not because no implementation can increment it, and the description now says so. No schema behaviour changed.

#### A8.6b Task-level reminder status and repair: implemented, awaiting architecture review

**The Task page can now answer the question `/attention` raises.** A8.6a told an Owner that a schedule stopped; A8.6b is where they find out what it means and do something about it. A reminder panel on the Task page shows the current schedule state in plain language and offers exactly three actions: set a due date, change it, or remove it. **No endpoint, no server action, no schema change, and no migration** — the `GET`, `PUT`, and `DELETE` routes A8.3b shipped were sufficient, which was the design intent.

**Server-rendered, client-interactive.** The Task page stays a server component and loads reminder state through the same service the `GET` route calls, so the panel is correct on first paint with no fetch waterfall and no loading flash on a page that already has the data available to it. Only the input, the two mutations, and the confirmation dialog are client code. The link from `/attention` carries **no query parameter and no deep-link state**: the panel is the Task's own reminder state and must be complete however the Owner arrived, and a parameter would create a second rendering path that only one route ever exercises.

**Editability is derived from the domain, not restated.** `decideReminderScheduling` already decides which Task statuses carry a schedule, so the panel calls it rather than re-listing them. A duplicated list that drifted would disable a working control or, worse, offer one the route would refuse with `409` — a button that predictably fails. A completed, dismissed, or otherwise ineligible Task therefore shows its reminder history with the controls disabled and the reason stated, which is also available to assistive technology rather than conveyed by the disabled attribute alone.

**Stop-reason copy is imported from the module `/attention` uses**, so the two surfaces cannot describe the same stop differently — an Owner who reads "delivery could not be confirmed" in the list must not read something subtly different on arrival. The Task page can say more than the list could: it knows the three _ordinary_ endings — completion, dismissal, due-date removal — and names them as normal endings rather than falling back to the list's deliberately non-committal sentence.

**D104 disclosure is shown before submission, not after.** Changing an existing due date starts a new reminder cycle, resets the overdue count, and recalculates every date; the panel says so while the Owner is still deciding. It stays silent when setting a _first_ due date and when re-saving the _same_ date, because neither restarts anything, and a disclosure that appears every time is one an Owner learns to dismiss without reading. "Cycle" is the Owner-facing word throughout — `generation` is never displayed, and neither is any claim, lease, fencing, or scheduler vocabulary.

**The date is a calendar date and is treated as one end to end.** The input is `type="date"`, validated for format and for Gregorian reality, and the exact `YYYY-MM-DD` string is what the request carries — no `Date` construction, no browser-local midnight, no timezone shift. Explanatory copy names the organization zone. There is no time picker: 09:00 organization-local is policy, not a preference.

**Removal is destructive to running automation, so it is gated.** The confirmation dialog follows the established handoff pattern — focus moved in, focus restored on close, Escape to cancel, an explicit checkbox before the confirm button enables — and it states that already-sent email **cannot be recalled**. Removal _stops_ the schedule rather than erasing it: the row survives with stop reason `due_date_removed` so the history stays inspectable, and the panel says "reminders ended when the due date was removed" instead of pretending the Task never had one.

**Ambiguity is never collapsed into "failed".** Six outcomes get six different sentences: confirmed success, validation failure, domain conflict, stale ETag, unknown transport outcome, and a failed re-read. A `412` is a **resolution path** — the panel re-reads authoritative state, replaces itself with it, and explains that the reminder changed elsewhere or the earlier request may already have applied — and it never silently retries with a fresh ETag, because that repeats an action the Owner did not reconfirm. An unknown transport outcome (D132) is reported as unknown and resolved the same way. `428` is treated as an implementation defect and is unreachable from the UI. No offline queue, no background sync, no local authoritative state.

**No resend control exists, in any state.** Not "send now", not "retry", not "restart", not "reset". D129 stopped the schedule deliberately and no resend policy is ratified; the only authorized lifecycle changes are the existing Task and due-date mutations. A source guard prohibits the vocabulary so the button cannot appear later by accident.

**A8.6b found a defect that made A8.3b's reminder API unusable from any real client.** `lib/reminders/etag.ts` imported `NO_SCHEDULE_REMINDER_VERSION` as a value from `@aicaa/db`. That package is a `serverExternalPackages` entry, so Next leaves it as a runtime external and the statically imported binding arrived **`undefined`** in the running server. Every Task without a schedule advertised `"task-reminder-<id>-vundefined"`; the `GET` returned it with a `200`, and every mutation presenting it was refused with a `412` describing a concurrency conflict that had never happened. **Setting a first due date over HTTP was impossible.** Nothing threw, no test failed, and no log recorded an error — unit tests resolve the package directly and no browser test had yet established a first reminder, so the A8.6b panel is the first caller to round-trip a no-schedule token through a real server. The constant is now declared in the web app, with tests asserting it still equals the persistence value and — the check that would actually have caught this — that the token it builds **parses**.

#### A8.6c Owner event notification visibility: implemented, awaiting architecture review

**A8.5 exists to email the Owner once per notable event. When that email is never sent, the Owner may never learn the event happened at all** — and until now no surface said so. A8.6c adds a second section to `/attention` answering one question: _what happened recently that Rocket could not tell you about?_ **No endpoint, no server action, no mutation, no schema change, no migration, and no new index.**

**It is deliberately not a notification inbox, and it is not a D108 requirement.** D108 asks for reminder discovery and repair, which A8.6a and A8.6b implement. This is a different and smaller thing: a bounded, read-only backstop for delivery that failed. There is no resend, no acknowledgement, no dismissal, no mark-as-read, and no history browser. An item leaves this surface exactly one way — by ageing out of the window — and that is the whole retirement mechanism by design. Adding a "mark as read" would turn a truthful record of what Rocket failed to say into a to-do list the Owner maintains.

**Four states are shown and four are not.** `suppressed`, `failed_permanent`, `ambiguous`, and `requires_owner_attention` all mean the Owner was never told. `sent` is excluded because the Owner already has the email and repeating it on a web surface is the inbox this is not. `pending`, `claimed`, and `failed_retryable` are excluded because they are still in progress: saying so would invite the Owner to act on a decision the worker has not finished making, which is how a page and a worker come to contradict each other.

**The three reminder-stop events are excluded in SQL, and that is correctness rather than de-duplication.** Section one of the same page is driven by `TaskReminderSchedule.requiresOwnerAttention`, which **clears** when the Owner sets a new due date. A notification intent is terminal and clears never. An unfiltered read would therefore keep announcing "we could not tell you reminders stopped" for a schedule the Owner repaired weeks ago, directly beneath the live section that no longer lists it. Filtering in the statement rather than after projection also keeps the bound honest: dropping rows in the presentation layer would let a full batch of fifty reminder stops render as an empty list while still reporting the batch as filled. `reminder.no_active_assignment` is **not** excluded — it never raises the attention flag, never reaches section one, and is invisible to the Owner today.

**Thirty days and fifty items are ratified product decisions, and they are enforced in different places.** The cutoff is computed by the caller, because nothing in `packages/db` reads a clock (D103). The ceiling is enforced inside the repository, so no caller can widen it — a limit of 51 is rejected, not clamped. The window is **not** a performance measure, and saying so would be a convenient untruth: measured on PostgreSQL 16.14 with 200,000 intents, the windowed and unbounded forms of the query cost the same 3,656 buffers and 0.50 ms, because `LIMIT 50` against a backward scan of the existing `(occurred_at, id)` index stops early either way.

**No index was added, on measured evidence rather than assertion.** A candidate `(organization_id, occurred_at, id)` index was built and measured during this slice. It helps the populated case — 61 buffers and 0.18 ms against 3,656 and 0.50 ms — and the planner **declines it** in the steady state, where every notification was delivered and the scan must walk the whole window to prove the answer is empty (20,522 buffers, 3.0 ms, identical with and without it, because no index covers `state`). Three milliseconds at a hundredfold Production's row count does not buy a permanent write cost. The shape to reach for if that ever changes is a partial index on the four visible states, not this candidate.

**Subject resolution is batched, because the obvious implementation is an N+1 that also leaks.** A per-row call to the existing single-subject resolver would cost fifty round-trips for a full page. Instead subjects are grouped by kind and resolved with at most one `IN` per kind: five statements at the very most — intents, three subject kinds, Tasks — whatever the row count, asserted flat at the driver. Every lookup independently repeats `organizationId`, because an intent deliberately holds **no foreign key to its subject** (so that purging a Task cannot delete a notification still owed), which makes their agreement an invariant of the write path rather than something the database enforces.

**An unresolvable subject renders without a link rather than disappearing.** A purged subject, a subject naming another organization's row, and an event about no Task at all are collapsed into the same outcome on purpose: an item with no link. Silently dropping the notification would be the one behaviour this surface cannot afford, since a thing Rocket failed to tell the Owner would then also be a thing the page failed to tell them.

**Who did it is a closed vocabulary of three words.** One shared module maps the audit actor category to "You", "The Recipient", and "Rocket". No Recipient identity is resolved: the category is all the Owner needs, and loading Recipient identity into a rendering path that has no other reason to hold it is how D134's boundary erodes. `attributionLabel` is never displayed here — it is a write-path display string and the field most likely to carry a Recipient's name. The A8.5 email renderer says "your assistant" where this says "Rocket", and that divergence is deliberate: inside the product, "your assistant" reads as a different actor from the one every other page calls Rocket.

**The projection carries nine fields and the internals are absent rather than unrendered.** `occurrenceKey`, claim holder, lease expiry, fencing sequence, attempt count, provider references, failure codes, request and correlation identifiers are not selected from the database at all, so they never exist in memory to be accidentally rendered. Recipient names, email addresses, OAuth state, tokens, capability URLs, Recipient-authored clarification text, and Gmail excerpts are unreachable from this path by construction.

**One server read per navigation, and failures reach the error boundary.** The section is a server component on the page that already exists. No endpoint, no polling, no refresh control, no client state machine. A database failure propagates to the boundary the page already has, for the same reason A8.6a gave: rendering "nothing went undelivered" on the strength of a missing table would be a lie of exactly the kind this surface exists to prevent. **`/attention` therefore now depends on the A8.5a migration as well as the A8.3a chain**, and neither is applied in Production.

##### A8.7a rollout preparation, recovery procedures, and verification classification: implemented, awaiting architecture review

**A rollout this size is decided in advance or improvised under pressure, and the second option is how a nine-migration change to a live database goes wrong.** A8.7a writes the whole procedure down while nothing is at stake. It contacts no production system, no database, no scheduler, and no provider; it changes no migration, no `vercel.json`, no environment variable, and no A8 runtime semantics.

**Three defects in the existing documentation were the reason this slice had to come first, and each would have caused a real failure.**

The runbook directed Prisma migrations through the Supabase **transaction-mode** pooler on port `6543`. `prisma migrate deploy` holds a **session-scoped advisory lock** for its whole invocation and transaction-mode pooling provides no session to hold it in, so the first production migration attempt in the project's history would have been made through an endpoint that cannot support it. The corrected strategy runs migrations from the operator workstation against the **session-mode** endpoint on port `5432` as a process-scoped override — no Vercel variable changes, no `directUrl` added to `schema.prisma`, and no new runtime database variable.

An earlier revision recommended applying `lock_timeout` to the migration's connection as protection for migration 1's `ACCESS EXCLUSIVE` lock on the live `tasks` table. **Every route to that is unavailable or unsound**: `SET lock_timeout` in a separate `psql` session governs only that session, `PGOPTIONS` is not read by Prisma's driver, a Shared Pooler need not preserve arbitrary startup options, editing the migration changes its checksum, and a later migration cannot protect an earlier one. It is replaced by operational controls that achieve the same end: a `pg_stat_activity` long-running-transaction check, an out-of-band `psql` lock probe that takes and immediately rolls back the same lock class, a scheduler pause, and `pg_cancel_backend` for in-flight containment — never `pg_terminate_backend`.

The failure model claimed more atomicity than exists. **No A8 migration contains an explicit `BEGIN` or `COMMIT`** — verified across all nine files — and no transaction spans migration files. PostgreSQL may treat a multi-statement query message transactionally, but that is emergent behaviour the runbook must not rely on. The consequence is procedural: after any failure the **physical schema is inspected**, and `migrate resolve` is never used from the migration-history row alone.

Future work should decide whether `build:web` should run before the affected tests or whether those tests should build their own required fixture — and must **preserve** packaging-test coverage rather than bypassing it. Documented only; **not** implemented by the development-process hardening pass.                                                                      |
| **Run database tests against a real PostgreSQL engine, not only PGlite** | PGlite executes the real migration SQL, so constraints, partial unique indexes, and enums are genuinely enforced — but it is a **single in-process connection**. No test can therefore contend two sessions on the same row, and every concurrency guarantee in the A8.3a audit is reasoned rather than proven. The same environment would enable a `prisma migrate diff` drift gate, which needs a live database and so is absent today; A8.3a is the first slice whose index names diverge from Prisma's defaults, and nothing currently detects schema-versus-migration drift in naming (audit F12). Requires Docker or a hosted test database, which is why it is backlog rather than a gate. |
